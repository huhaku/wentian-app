# Android 天气应用系统架构

## 1. 架构概述

当前应用采用 **MVVM + Repository Pattern**，并结合 Hilt、StateFlow、WorkManager 构建完整的天气展示、城市搜索、后台更新与设置能力。

当前实际代码路径为：`app/src/main/java/info/ggdog/weather/`

---

## 2. 当前实际分层

```text
┌────────────────────────────────────┐
│ presentation/ui                    │
│ WeatherScreen / LocationSelection  │
│ SettingsDialog / MainActivity      │
├────────────────────────────────────┤
│ presentation/viewmodel             │
│ WeatherViewModel                   │
│ LocationViewModel                  │
│ SettingsViewModel                  │
├────────────────────────────────────┤
│ domain                             │
│ model / repository                 │
├────────────────────────────────────┤
│ data                               │
│ api / mapper / model / repository  │
├────────────────────────────────────┤
│ worker / receiver / util / widget  │
└────────────────────────────────────┘
```

### 2.1 分层职责

| 层级 | 主要职责 |
|------|----------|
| UI 层 | 展示天气、搜索城市、展示错误和设置界面 |
| ViewModel 层 | 管理页面状态、发起加载、组织交互逻辑 |
| Repository 层 | 聚合天气接口、搜索接口、配置和兜底逻辑 |
| API / DTO / Mapper | 接口访问、响应解析、模型转换 |
| Worker / Receiver | 后台天气更新、定时任务触发 |
| Widget | 桌面小部件展示与联动 |

## 4. 数据流说明

### 4.1 天气数据获取流程

```text
WeatherScreen
  ↓
WeatherViewModel
  ↓
WeatherRepository
  ↓
QWeatherApi
  ↓
WeatherMapper
  ↓
Weather UI State
```

流程说明：
1. 页面加载时由 `WeatherViewModel` 发起天气请求
2. `WeatherRepositoryImpl` 调用真实天气接口
3. 通过 `WeatherMapper` 转换为领域模型
4. UI 根据 `Loading / Success / Error` 状态渲染

### 4.2 城市搜索流程

```text
LocationSelectionScreen
  ↓
LocationViewModel
  ↓
LocationRepositoryImpl
  ↓
QWeatherGeoApi
  ↓
SearchResponse -> Location
```

关键点：
- 城市搜索与天气接口已拆分
- 搜索无结果时返回空列表
- 400/404 不再视为页面错误

### 4.3 后台更新流程

```text
MainActivity / Helper
  ↓
WorkManager
  ↓
WeatherUpdateWorker
  ↓
WeatherRepositoryImpl
  ↓
更新 UI / Widget / 缓存数据
```

## 5. 当前状态管理

### 5.1 天气状态
主天气页采用典型三态：
- Loading
- Success
- Error

### 5.2 城市搜索状态
当前已显式区分：
- Idle
- Loading
- Success
- Error

这样可以正确区分：
- 尚未搜索
- 正在搜索
- 搜到结果 / 无结果
- 真正请求异常

## 6. 网络架构说明

### 6.1 当前 Retrofit 架构
当前已按职责拆分两套 Retrofit：

| Retrofit | 用途 |
|----------|------|
| weatherRetrofit | 实时天气、预报、AQI、日出日落 |
| geoRetrofit | 城市搜索 |

### 6.2 拦截器职责
统一网络拦截器负责：
1. 根据配置重写 host / scheme / port
2. 自动追加 API Key 查询参数
3. 添加统一 User-Agent

### 6.3 配置兼容策略
`ApiConfigProvider` 负责：
- 默认 URL
- 默认 API Key
- 旧 `devapi.qweather.com` 配置迁移
- 输入 URL 自动补全 `https://`

## 7. 与旧文档的主要差异

当前架构与早期设计相比，已有这些变化：
1. 包路径已从旧示例路径切换为 `info.ggdog.weather`
2. 并未引入独立 `core` 模块、`usecase` 目录和导航模块
3. 设置页当前为 `SettingsDialog`，不是独立 `SettingsScreen`
4. 城市搜索页合并在 `LocationSelectionScreen` 中，不是独立 `SearchScreen`
5. 当前以 `SharedPreferences + Repository` 为主，Room 仍属保留结构
6. 网络层已专门拆分 GeoAPI，而不是单一天气 API

## 8. 当前架构结论

当前系统架构已覆盖以下核心闭环：
- 天气查询
- 城市搜索
- API 配置
- 错误处理
- 后台刷新
- 小部件支持

后续演进重点建议为：
1. 完善城市持久化
2. 强化 Room 缓存落地
3. 补充测试体系
4. 增加更细粒度的错误分类与监控
