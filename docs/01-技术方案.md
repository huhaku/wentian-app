# Android 天气应用技术方案

## 1. 项目概述

本项目是一款面向 Android 平台的原生天气应用，应用名称为 **天气**，包名为 `info.ggdog.weather`。当前项目已从早期 Mock 数据原型阶段推进到 **真实和风天气 API 对接与功能联调阶段**。

应用目标是在保持简洁中文界面与稳定交互体验的前提下，提供：
- 实时天气
- 24 小时预报
- 7 天预报
- 空气质量
- 城市搜索与切换
- 桌面小部件
- 后台定时更新
- 基础设置能力

---

## 2. 技术选型结论

### 2.1 开发方式
**最终采用：原生 Kotlin + Jetpack Compose**

原因：
1. 桌面小部件、后台更新、系统广播、WorkManager 等能力依赖 Android 原生生态
2. 天气应用对前后台切换、状态恢复、性能和系统兼容性有较高要求
3. Compose + Kotlin + Hilt 的组合更适合当前项目的中长期维护

### 2.2 当前技术栈

| 类别 | 技术选型 |
|------|----------|
| 语言 | Kotlin 1.9.24 |
| UI | Jetpack Compose 1.6.7 |
| 设计系统 | Material Design 3 |
| 架构 | MVVM + Repository |
| 状态管理 | StateFlow + collectAsStateWithLifecycle |
| 依赖注入 | Dagger Hilt 2.48 |
| 网络 | Retrofit + OkHttp + Moshi |
| 后台任务 | WorkManager |
| 本地存储 | SharedPreferences + Room（结构保留） |
| 构建工具 | Gradle 8.7 |

---

## 3. 架构方案

### 3.1 总体架构
采用 **MVVM + Repository Pattern**。

```text
UI(Compose)
  ↓
ViewModel
  ↓
Repository
  ↓
Remote API / Local Cache / Preferences
```

### 3.2 分层职责

| 层级 | 职责 |
|------|------|
| presentation | 页面渲染、状态展示、用户交互 |
| viewmodel | 组织页面状态与用户动作 |
| domain | 核心模型与仓库接口 |
| data | API、DTO、Mapper、Repository 实现 |
| worker/receiver/util | 后台更新、广播、系统辅助能力 |

### 3.3 当前实际模块
- `WeatherViewModel`：天气页状态与加载
- `LocationViewModel`：城市搜索、城市选择
- `SettingsViewModel`：刷新间隔与 API 配置
- `WeatherRepositoryImpl`：真实天气数据获取
- `LocationRepositoryImpl`：城市列表与 GeoAPI 搜索
- `WeatherUpdateWorker`：定时更新任务

---

## 4. 网络与 API 方案

### 4.1 天气服务
当前接入 **和风天气 QWeather**。

### 4.2 当前鉴权方式
当前代码已使用 **旧版 API Key 查询参数**，未采用 JWT。

### 4.3 当前接口拆分策略
为了避免天气接口与城市搜索接口混用导致路径或 host 错误，当前代码已拆分为两套 API：

| 接口类型 | 说明 |
|----------|------|
| `QWeatherApi` | 天气、AQI、日出日落等天气数据接口 |
| `QWeatherGeoApi` | 城市搜索 GeoAPI |

### 4.4 当前网络实现特点
1. 使用 OkHttp 拦截器统一追加 `key`
2. 通过 `ApiConfigProvider` 读取 URL 与 API Key
3. 支持默认 API 配置
4. 对旧错误 host 做兼容迁移
5. Moshi 已加入 Kotlin 反射适配，避免 Converter 创建失败

---

## 5. 数据与缓存策略

### 5.1 当前策略
- 天气数据走真实接口
- 城市搜索走 GeoAPI
- 未配置 API 时城市列表可使用内置兜底数据
- 搜索无结果时按空列表处理，不作为异常抛出

### 5.2 本地存储现状
- `SharedPreferences`：已实际用于 API URL / API Key / 刷新间隔等配置
- `Room`：结构已保留，但当前主要能力仍以在线查询和轻量兜底为主

---

## 6. 后台更新方案

当前已实现：
- `WeatherUpdateWorker`
- `BackgroundTaskHelper`
- `BatteryOptimizationHelper`
- `WeatherUpdateReceiver`

能力说明：
1. 可配置刷新间隔
2. 最小刷新间隔 15 分钟
3. 启动后可调度周期性天气更新
4. 支持手动立即更新

---

## 7. UI 与交互约束

### 7.1 固定要求
- 所有界面与提示均为简体中文
- 保持现有前端样式和用户交互体验不被真实 API 接入破坏
- 天气主界面、24 小时预报、7 天预报、错误页、设置页均已稳定落地

### 7.2 当前关键交互
- 错误页可直接填写 API URL / API Key
- 错误信息可复制
- 保存后可直接重试
- 城市搜索无结果显示空态，而不是报错

---

## 8. 安全性说明

### 8.1 当前现状
当前 API Key 支持在应用内配置，便于调试和测试，但这并非强安全方案。

### 8.2 当前建议
1. 不在代码中散落硬编码 Key
2. 统一通过 `ApiConfigProvider` 管理
3. 后续如进入正式发布阶段，可考虑服务端代理或更严格密钥保护策略

---

## 9. 当前方案结论

当前技术方案已经从“原型设计”转为“可运行的真实天气应用方案”，重点特征是：
- 原生 Kotlin + Compose
- MVVM + Repository
- 真实和风天气 API 对接
- 城市搜索独立 GeoAPI
- API Key 模式
- 后台更新可用
- 城市搜索、错误页、默认配置、默认广州等关键体验已打通

后续重点不再是基础方案选择，而是：
- 持久化增强
- 自动化测试补充
- 兼容性测试
- 错误提示与缓存能力继续完善
